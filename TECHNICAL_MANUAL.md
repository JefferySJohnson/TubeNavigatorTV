# TubeNavigatorTV — Technical Manual (v1.19 (20), 24 Nov 2026)

Status-only Apple TV companion to TubeNavigator (iPhone/iPad). Seven tabs, no journey planning.

## UI

- Classic `.tabItem` API (not the tvOS 18 `Tab` syntax), so the app runs on tvOS 17+.
- **Status tab**: `NavigationStack` + `ScrollView` + `LazyVStack`. **v1.11:** at the very top sits the shared `RefreshHeaderRow` — the footer row is gone everywhere, and the version text lives only in Settings. **v1.13:** the header row is right-aligned now — the tab's title (when a tab has one) sits on the left, and "Updated HH:mm" + Refresh sit at the upper right (`.subheadline`), so the middle of the screen is free. Tabs without a title just get the right-aligned controls. Focus note (v1.13, verified): Down from the tab bar skips the right-aligned Refresh and lands on the content — the same as the v1.8 gear, which the focus engine skipped entirely — but Up from the top content row lands on Refresh, and Up from Refresh returns to the tab bar, so it stays reachable by remote. Weather strip (London, temperature, condition, H/L, "Data from Apple Weather" attribution) below it — v1.3 shrank it (temperature 96pt → 64pt, "London" `.largeTitle` → `.title`, condition and H/L `.title2` → `.title3`) because it hogged the top third. **v1.8:** the condition gets its WeatherKit icon next to the text (SF Symbol from `symbolName`), and a 7-day forecast strip sits under the strip (day, icon, high/low, from `dailyForecast` in the same WeatherKit call) when the Settings toggle is on — with the strip on, the bottom of the grid sits below the fold and needs a small scroll; the toggle turns it off and restores the one-screen fit. **v1.16: the forecast row is a Button that cycles the view** — 7 days → next 12 hours → today — on each press, with a hint under the row ("Tap for hours" / "Tap for today" / "Tap for 7 days"). Only the forecast row is the button (a pill around the whole weather strip would be a giant white block). The mode is a `ForecastMode` enum (sevenDay/hours/today) persisted in `@AppStorage("TubeNavigatorTV.forecastMode")`, so his pick sticks across launches. Hours view: 12 columns from the next full hour (hour in London time, icon, temp) from `@Published var hourly` — see Weather below for the sort fix. Today view: condition, H/L, rain chance, sunrise/sunset (from `DayWeather.sun`, see below). Down from the tab bar now lands on the forecast row before the line buttons — one extra focus stop. **v1.11:** the centred "⚙ Settings" row below the strip is gone — Settings is now the last tab (see below). Then a two-column `LazyVGrid` with one button per line — colour dot (24pt, with a thin white ring, so the Northern line's black dot stays visible) + line name (`.title3` bold) + status word (`.headline` semibold, green Good Service, orange otherwise), all thirteen on one screen. v1.3 removed the buttons' grey fill — the rows are just text on the dark background, so the grid reads as a list, not a wall of boxes. A `@FocusState` tracks the focused line and its status word goes **black** when focused (green/orange on the white focus pill washed out). **v1.5/v1.6: each button is capped in width (720pt in v1.6) and left-aligned in its column** (`.frame(maxWidth: 720, alignment: .leading)` on the `NavigationLink`, grid `alignment: .leading`) — the focus pill hugs the button, not the full 919pt column, so it is much smaller, while Bakerloo stays at the left edge and Central stays in the middle. Button vertical padding is 4pt (tightened in v1.4, kept). Tapping a button pushes `LineDetailView` (line name, status, full `reason` text, and a "‹ Back to all lines" button that dismisses).
- **Live tab (v1.9):** a third tab, `LiveView` (`NavigationStack` + `ScrollView`), with a "Live views" title, a one-line explainer ("TfL traffic cameras — a short clip, refreshed every few minutes. Tap a camera to watch it."), and one row per camera: the camera's still image as a 352×288 thumbnail (the clip's native size, shown as-is rather than upscaled into a blur), the display name, the camera's TfL name, and "Tap to watch" — or "Unavailable right now" in orange with the row dimmed and the link disabled when the API says `available` is false. The list comes from `fetchCameras()` (the full 889-camera list, ~1.1 MB, fetched once when the tab first appears and on Refresh) filtered to the six-name shortlist in `TubeService.liveCameraShortlist`. The player is paused on disappear. **v1.11:** the footer is gone; the shared `RefreshHeaderRow` sits at the top of the tab.
- **Map tab (v1.10):** a fourth tab, `MapView` (`ScrollView` + `VStack`, no `NavigationStack` — nothing pushes from it). Left: the Tube diagram (`Image("TubeMap")`, the September 2026 TfL map cropped to the diagram, 990×680, shown at 1150×790) with the selected line's path drawn over it — a white under-stroke (14pt) then the line's own colour (9pt), over a `Color.black.opacity(0.45)` dim of the rest of the map. Right (a fixed 666pt column): a two-column `LazyVGrid` of the thirteen line buttons (colour dot 20pt + name `.title3` bold, no status word — that lives in the panel) and, underneath, the status panel (line name `.title2` bold + status word `.title3` green/orange + the full reason `.headline` secondary, or "No further detail from TfL right now."). The button rows follow the live `lineStatuses` order, which is alphabetical (Bakerloo, Central, Circle, DLR, District, Elizabeth line, Hammersmith & City, Jubilee, Metropolitan, Northern, Piccadilly, Victoria, Waterloo & City) — DLR sits before District, so Down from Circle lands on District, then Hammersmith & City. A `@FocusState` tracks the focused button and `.onChange` sets the selected line, so the highlight and the panel follow focus — no tap needed. The line paths come from the `MapLines` data asset (`MapLinePaths.shared`, decoded from `NSDataAsset` as `[String: [[[Double]]]]` then mapped to `CGPoint` — `CGPoint` is not `Decodable` from `[x, y]` arrays, so the raw decode is nested double arrays). The button rows come from the live `lineStatuses` when loaded, else a static fallback list of the 13 ids/names, so the tab works before the first fetch. **Layout lesson:** the grid must sit in a width-constrained column — the first v1.10 cut used a two-column grid in an unconstrained `VStack` and the flexible columns collapsed to ~240pt, truncating "Hammersmith & City" and "Waterloo & City"; a single-column list fixed the names but pushed the status panel below the fold; the final form is the two-column grid inside the explicit 666pt column (1848 content − 1150 map − 32 spacing), which fits all thirteen names at full size with the panel on screen. **Known minor:** the panel's line name wraps to two lines for the longest names ("Waterloo & City" shows as "Waterloo / & City") — it has no `.lineLimit(1)`; still open, see the fix-up list. In v1.10 the Map footer (Refresh + Updated + version, `.subheadline`, same pattern) sat just below the fold and Down from the last grid row did not reach it (focus will not travel to the off-screen Refresh button) — the version was verified from the build instead (pbxproj grep 1.10/11 + the new tab visibly running). v1.11 removed all footers, so this is retired.
- **Boards tab (v1.11; two-screen since v1.14):** a fifth content tab. `BoardsView` is the station picker (a full-screen list of the seven stations since v1.15 — Paddington, Canary Wharf, King's Cross St. Pancras, Liverpool Street, London Bridge, Victoria, Waterloo — station name + coloured line dots per row); tapping a station pushes `StationBoardView`, a full-screen board for that station: the station name + Refresh + Updated in a header row, the line buttons across the top (dot + name, selected gets a white 0.22 highlight), then one section per platform, **five trains each** (v1.14 restored five — the v1.13 four was the fit for the shared screen; the detail screen has room) — destination (+ "via" on the Elizabeth line) left, minutes right, the train's current location in secondary text. **v1.12:** each train also shows its arrival clock time in London time next to the minutes ("60 mins 05:48", `arrivalTimeText`, secondary `.title2`). **v1.13:** the "Departure boards" title moved into the header row (left, with Updated + Refresh upper right), the separate title row is gone, and the board text shrank two steps — destination, minutes and arrival time `.title2` → `.headline`, via/location `.headline` → `.subheadline`, platform header `.title2` → `.title3` — with tighter spacing (content padding 36 → 20, VStack spacing 20 → 12, picker padding 10 → 6, board spacing 20 → 12, platform spacing 12 → 4), and four trains per platform instead of five — so both platforms fit on one screen at Paddington + Elizabeth line. The first cut (title3 rows, five trains) still left Platform B below the fold; the headline rows + four trains fixed it. **v1.14:** the two-screen split (picker → `StationBoardView` via `NavigationStack`); the "arriving" label (see Data); the arrival sound (see below); the board is indented (`.padding(.horizontal, 120)`) so destination and minutes sit closer together. **v1.15:** the "Back to stations" button is gone — the remote's Menu/Back button returns to the picker (the line buttons + Refresh are focusable, so the pushed screen holds focus and Menu pops back, unlike the v1.2 detail lesson). **v1.16:** focus-driven line switching — moving the pill Left/Right across the line buttons switches the board, no Select needed (`@FocusState private var focusedLine: String?` on the buttons + `.onChange(of: focusedLine)` sets `lineId`; there is no `.onFocusChange` modifier in SwiftUI — the compiler says so — so this is `@FocusState` + `.focused` + `.onChange`; the line buttons were extracted into `lineButton(_:)` because the ForEach + Button + label in one expression was too much for the type-checker, and that extraction surfaced the `.onFocusChange` error); the task restarts on `lineId` and the old trains stay until the new fetch lands (`loadedStationId` — clear `arrivals` only when the station changes, not the line), and `fetchArrivals` ignores `CancellationError` so rapid moves don't flash an error; the header (station name + Refresh + line row) is pinned in a `VStack` outside the `ScrollView` — only the trains scroll (v1.16 sticky header); the platform sections sort alphabetically by platform name (`sorted { $0.platform < $1.platform }`) so A is always on top at Paddington instead of the soonest platform leading. **v1.18:** the Paddington Elizabeth line board shows only A and B — `fetchArrivals` drops the mainline-platform rows (see Data). Default: Paddington + Elizabeth line. It auto-refreshes every 30 s via a `.task(id: "\(station.id)|\(lineId)")` loop that restarts whenever the station or line changes. Data comes from `fetchArrivals` (see Data below); the ghost-train filter and the two-stop-point rule are documented there. Note: a station with more than two platforms (Liverpool Street Elizabeth line has four — Platform 16, Platform 17, A, B; Canary Wharf DLR has six) still scrolls; the one-screen fit is for two-platform boards. **Arrival sound (v1.14):** a soft bong when a train on the open board first drops to a minute or less — seeded silently from the first fetch (a train already under a minute when the board opens does NOT bong; only trains that cross into "arriving" while the board is open do), once per train (tracked by `vehicleId` in a `bonged` set, reset per line). Three synthesized WAVs as `NSDataAsset`s (Bong 311 Hz 1.6 s, Chime C5→G4 1.3 s, Bell 880 Hz 1.1 s; peak 0.38, player volume 0.5). DLR is silent by design (vehicleId always empty). Settings "Sound" section: "Arrival sound" toggle (default on) + Bong/Chime/Bell picker. The trigger was verified on the simulator via a temporary debug print (three fires, each on a crossing, never on open); the print was then removed. Sound quality is Jeffery's to judge on the TV. Benign Xcode "AVAudioSession Hang Risk" warnings (issues 23755, 3271) appear in the console — noted, not fixed.

Top: the shared `RefreshHeaderRow` with the title "Elizabeth Line live map" + Updated + Refresh. Middle: the schematic — `ElizabethLineMap` in TubeService.swift holds all 41 station coordinates and the five chains, transcribed from `workspace/research_notes/elizabeth-live-map/stations.json` (PDF points on the 3251.34×793.701 diagram) and verified programmatically against it, zero mismatches. The map is 1848pt wide (~451 tall, 4:1), so it fits the 16:9 screen with the header above and the detail strip below. Left/Right use `ElizabethLineMap.lineNeighbour` to move to the next train on the same route and never jump branches. Up/Down use `branchNeighbour`: Up takes the northern branch and Down the southern branch (Shenfield ↔ Abbey Wood and Heathrow Terminal 5 ↔ Terminal 4; a train on the main chain takes the nearest train on the requested side). ## Data — TfL Unified API

`https://api.tfl.gov.uk`, free, no key required (~50 req/min anonymous).

- Status: `GET /Line/Mode/tube,dlr,elizabeth-line/Status`
- Planned: `GET /Line/{explicit-line-ids}/Status/{start}/to/{end}` — the dated path only works with explicit line IDs; the `/Line/Mode/...` form of that path 404s. The 13 IDs are baked in: bakerloo, central, circle, district, hammersmith-city, jubilee, metropolitan, northern, piccadilly, victoria, waterloo-city, dlr, elizabeth.
- Boards (v1.11): `GET /Line/{lineId}/Arrivals/{stopPointId}` — per line, per stop point. Fields used: destinationName, timeToStation (seconds), platformName, currentLocation, direction, towards, expectedArrival. **currentLocation is empty on the Elizabeth line** (checked live 23 Nov 2026 — every row at Paddington had `""`, so the board shows no location text there) but populated on Tube lines (e.g. Bakerloo "Queen's Park North Sidings", "Between … and …") and on the Jubilee line at Canary Wharf (every row — "Left Canada Water", "Approaching Canary Wharf"). Seven stations since v1.15 (Jeffery's list — the main termini, plus Canary Wharf; King's Cross and St Pancras share one Tube station, so they are one entry), with the lines each serves (ids from the iOS app's `StationData.swift`, cross-checked against the TfL StopPoint API for Paddington, Oxford Circus, Green Park, Bank, Liverpool Street and Waterloo): Paddington 940GZZLUPAC [elizabeth, bakerloo, circle, district, hammersmith-city]; Canary Wharf — Elizabeth line 910GCANWHRF, Jubilee line 940GZZLUCYF, DLR 940GZZDLCAN [elizabeth, jubilee, dlr]; King's Cross St. Pancras 940GZZLUKSX [circle, hammersmith-city, metropolitan, northern, piccadilly, victoria]; Liverpool Street 940GZZLULVT [elizabeth, central, circle, hammersmith-city, metropolitan]; London Bridge 940GZZLULNB [jubilee, northern]; Victoria 940GZZLUVIC [circle, district, victoria]; Waterloo 940GZZLUWLO [bakerloo, jubilee, northern, waterloo-city]. The six-station list it replaced (v1.13–v1.14) was the same minus Canary Wharf; the eight-station list it replaced (v1.11–v1.12): Paddington, Bank 940GZZLUBNK [central, dlr, northern, waterloo-city], Green Park 940GZZLUGPK [jubilee, piccadilly, victoria], King's Cross St. Pancras, London Bridge, Oxford Circus 940GZZLUOXC [bakerloo, central, victoria], Victoria, Westminster 940GZZLUWSM [circle, district, jubilee]. **Two-stop-point stations (proven live):** Paddington and Liverpool Street — their Tube lines answer to the 940GZZLU… id, their Elizabeth line platforms to the 910G… rail id (`910GPADTON`, `910GLIVST`; Liverpool Street's lineGroup confirms elizabeth sits under 910GLIVST, checked 23 Nov 2026) — `BoardStation.arrivalsId(for:)` returns the rail id only for lineId "elizabeth". Canary Wharf needs three (see above; from the HUBCAW line groups, checked live 23 Nov 2026). Hub ids (HUBBAN etc.) are accepted by the endpoint (`/StopPoint/HUBBAN/Arrivals` returns `[]`, HTTP 200) but the 940GZZLU ids are used. **Ghost-train filter (found live, fixed in v1.11, refined in v1.14):** before service starts the feed emits placeholder rows — timeToStation ~41 s, expectedArrival "now", empty currentLocation/towards, timeToLive far in the future — and they can carry any platform ("Platform Unknown", "A", "B", "Platform 10", "Platform 11" all observed), so filtering on platformName fails. The v1.11 rule (drop `timeToStation < 300 && currentLocation.isEmpty`) silently dropped every Elizabeth line train within 5 min, because Elizabeth rows NEVER carry currentLocation. The DLR feed gives every row the same prediction id (`-937089209`) and an empty vehicleId, and its copies differ in raw `timeToStation` seconds, so v1.15's composite key (id + platform + destination + timeToStation) never matched. v1.16 changed the key to (predictionId + platform + destination + clock HH:mm) — and it STILL triplicated. The real cause, found 23 Nov 2026 by reading the raw feed with curl and a temporary debug print: **the DLR feed returns 16 distinct trains, no copies at all** (decoded=16, afterDedupe=16) — the triplication was never in the data. Verified: the DLR board shows each train once with its own time (Platform 1 Lewisham 1/6/11 mins, Platform 2 Lewisham 3/7/12 mins, Platform 3 Stratford 5/11 mins), and the duplicate-id warning is gone. **DLR feed quirk that remains:** each train is listed under BOTH platforms of a pair (Platforms 1 & 2 both serve Lewisham with the same three trains, 3 & 4 Stratford, 5 & 6 Bank — identical expectedArrival and timeToStation), so the same train appears once on each of its two platforms. That's what the feed says; collapsing it would hide a platform the train might actually use. The debug prints were removed after the fix (no `print(` in TubeService.swift).

**Live Map positions (v1.17) — the Elizabeth line is the exception.** `GET /Line/elizabeth/Arrivals` (line id `elizabeth`, NOT `elizabeth-line`) returns ~2,000 rows, and `currentLocation` is blank on every row — the Elizabeth line feed never says where a train is, so positions are estimated from `timeToStation` + the station sequence (the same algorithm as the web live-map page, `workspace/research_notes/elizabeth-live-map/positions.py`, ported to Swift as `fetchElizabethLinePositions()`). Dedupe by `vehicleId` (unique per train; each train appears at many stations). Station names normalised the same way as the web page (strip " Rail Station"/" Underground Station", leading "London ", " (Berks)"/" (London)"; "Heathrow Terminals 2 & 3 Rail Station" → "Terminals 2 & 3"). Ghost filter: the same rule as the Boards (drop when timeToStation < 300 AND currentLocation empty AND timeToLive > expectedArrival + 120 s) — never drop on empty currentLocation alone, or every Elizabeth train within 5 min would vanish. In-service only: a train shows when its next arrival is ≤ 30 min away. Position: next station = min timeToStation; direction from destination (eastbound: Shenfield/Abbey Wood/Gidea Park; westbound: Reading/Maidenhead/Terminal 4/Terminal 5/Paddington); previous station = the neighbour of next on the FULL chain on the side it came from — Abbey Wood-branch trains have NO Stratford row in the feed though they pass through it, so the interpolation runs along the full chain, not the feed's sparse list; Heathrow trains never call at West Drayton. Segment running time R = the median timeToStation difference between adjacent chain stations, computed from the fetched data itself (≥2 samples, fallback 240 s — e.g. Paddington→Bond Street 240 s, Bond Street→Tottenham Court Road 120 s, Liverpool Street→Whitechapel 150 s, Whitechapel→Stratford 360 s, Hayes & Harlington→Southall 180 s, Acton Main Line→Paddington 540 s); fraction = clamp(1 − timeToStation/R, 0, 1); interpolate along the polyline through intermediate chain stations. Edge cases: next=Stratford heading west is ambiguous (Maryland vs Canary Wharf) — placed at Stratford on first sight, vehicle history (`previousPositions`) resolves it after; next=Hayes heading east defaults to previous=West Drayton unless history shows the Heathrow branch; Terminals 2 & 3-east uses history for Terminal 4 vs 5. A train with no previous station sits at its next station, by design. Validated before building by running a Python mirror of the Swift logic against a live feed snapshot (1,999 rows, 132 vehicles): 72 in-service trains (34 east, 38 west), 8 with no previous station, 0 out-of-bounds, 0 non-finite. Tube lines are the opposite — they DO report real positions ("Between X and Y", "At X", "Approaching X"), so a true-position map is possible there; the DLR is the other exception (no location text). A Circle line true-position map is an offered follow-up, not built, not authorised.

### London time

TfL times are London wall-clock time. `dayTitle` and `timeRange` use `DateFormatter`s with `TimeZone(identifier: "Europe/London")` — deliberately, because on a US device the device zone (EST, UTC-5) shifts early-morning London times back to the previous evening. Same fix as the iPhone app, 17 Nov 2026 (v1.4). `parseISODate` is a plain `ISO8601DateFormatter`.

## Icon — tvOS App Icon & Top Shelf Image

tvOS icons are **not** a plain `.appiconset` with tv-idiom slots. `actool` rejects that ("None of the input catalogs contained a matching App Icon & Top Shelf Image brand assets collection", plus "unassigned children"). tvOS needs an **`App Icon & Top Shelf Image.brandassets`** folder:

- `App Icon.imagestack` — 400×240 @1x, 2x; Front/Back imagestacklayers. In an imagestack's Contents.json the **first** layer listed is front-most and the **last** must be fully opaque. Front layers are transparent PNGs, back layers opaque.
- `App Icon - App Store.imagestack` — 1280×768 @1x.
- `Top Shelf Image.imageset` — 1920×720 @1x, 2x.
- `Top Shelf Image Wide.imageset` — 2320×720 @1x, 2x.
- A brand `Contents.json` with an `assets` list (roles `primary-app-icon`, `top-shelf-image`, `top-shelf-image-wide`).
- `ASSETCATALOG_COMPILER_APPICON_NAME = "App Icon & Top Shelf Image"` in the pbxproj.

Script: `~/workspace/tube-navigator-tv/make_tv_brandassets.py` generates all 24 files (front layers = Jeff roundel on transparent RGBA, back layers = opaque white RGB; top shelf = **white** banner with the normal roundel + "TubeNavigator" in TfL blue — a Tube-red banner was tried first and hides the red ring). Two rendering bugs were found and fixed by visual check: (1) a double-supersample bug in the text-size limits made JEFF render ~2× too large for the bar (fixed: limits computed in the canvas's own pixels, ink height ≈ 75% of bar height); (2) the red-banner top shelf. Final images verified on screen: 400×240 front layer and 1920×720 shelf both look right. The old `AppIcon.appiconset` was trashed on the Mac. This format is also recorded in `~/AGENTS.md`.

### Reported bug — theme unreadable under one system appearance (Jeffery, 23 Nov 2026 ~08:20 EST — FIXED in v1.14)

- **What he saw:** his Apple TV's system appearance switched, and the app became unreadable — black background with black lettering, on the Midnight theme. He had to switch the system setting back to light to read it.
- **Cause (read from the code):** the app's backgrounds are fixed dark — Midnight is `.black`, the other three themes are fixed dark tints — but the lettering mostly uses the system's own colours (`.primary` / `.secondary`), which follow the TV's appearance setting. The app never tells the TV "I'm a dark app, keep my text light", so when the system and the theme disagree, the text can come out black on a black background.
- **Fix (v1.14):** one change at the app root — `.preferredColorScheme(.dark)` on `ContentView`, so the text stays white/light whatever the system is set to. The white focus pill is untouched (focused text already goes black on it, v1.3). Verify on the simulator with the system appearance set to light, to prove the app stays readable — not yet done (the fix is code-level so far).

## Lessons carried forward

- Check the destination from the settled "Running … on …" status after every run, not a transient flash (the v1.9 iPhone run flashed the wrong destination first). Here the destination was already the TV simulator; on 20 Nov 2026 an unchecked destination installed the iPhone app on his real iPhone.
- Approval cards time out if unanswered and the step does not run — report and ask before retrying; never retry on your own.
- The Reports navigator (not the status line, not the Build Results outline row) is the record of what ran.
- Window IDs change between sessions (Xcode 6850, Device Hub 7002 on 22 Nov 2026) — always re-list. Window lists are Space-filtered; if a window vanishes, the Mac may have switched Spaces.
- Tab switching on tvOS is focus-driven: Up to the tab bar, then Left/Right switches immediately — Return/Select is not needed, and pressing it with focus elsewhere does nothing useful. A segmented Picker inside a ScrollView + LazyVStack is skipped by the focus engine (Down from the tab bar goes straight to the first card; Up from the first card does nothing) — fixed in v1.1 by replacing it with centred Buttons, which always take focus. A left-aligned control is skipped too; centring is part of the fix.
- In the Device Hub, element clicks work on chrome buttons and AX controls; coordinate clicks work on the simulator screen itself. `double_click` delivers a real tap where single clicks fail (iPhone simulator). `screen.snap` saves `/home/hatch/workspace/nodes/<uuid>/screen-window.jpg`; read it with `muse.read` and ground points with `muse.visual_grounding` on a fresh screenshot before clicking. Drags sent while the window is in the background do not drop — the window must be frontmost.
- A `LazyVGrid` with flexible columns inside an unconstrained `VStack` in a `ScrollView` collapses: the columns size to content (~240pt) instead of dividing the screen, truncating long names. Give the column an explicit width first (the Map tab's right column is `.frame(width: 666)`), then the flexible columns divide it properly.
- Focus will not travel to an off-screen footer button: on the Map tab, Down from the last grid row (and the on-screen Down button) leaves focus where it is instead of scrolling the Refresh button into view. Judge the version from the build (pbxproj grep + the new UI running) when the footer cannot be sighted.
- **tvOS focus and the Menu button:** a pushed detail view with no focusable element holds no focus, and the remote's Menu/Back button then exits the app to the Home Screen instead of popping back (seen twice on the v1.2 detail). Give every pushed screen a focusable element — a "Back" button is the reliable fix, and it was verified. The Device Hub AX tree does not show tvOS focus movement (repeated arrow-key presses report "no change observed" even while focus visibly moves) — judge focus from screenshots, not the tree. The Device Hub's on-screen Down/Up buttons (click_element) also drive the remote and can scroll a list into view when keyboard arrows stall.
- **Destination switching:** the popover's row clicks are unreliable — `click_element` on a row can close the popover without selecting, and `select_popup` opens it but selects nothing. The reliable route is the Filter field: type a distinguishing fragment (e.g. "1080p"), the list narrows to the one matching row (already selected), then press Return to commit and check the popupbutton value. The popover is an unbound window on the second display; do not click its rows by coordinates grounded from a `screen.snap` of it (the snap is a scaled full-screen image and the click does not land).
- **Small icon buttons in a corner are skipped by the tvOS focus engine.** A gear icon button in the weather strip's top-right corner (v1.8) never took focus: Down from the tab bar went straight to Central, Up from Central went back to the tab bar, and a coordinate click did not focus it either. Centred rows take focus reliably (the Planned range buttons, the "⚙ Settings" row) — put anything the remote must reach in a centred/full-width row, not a corner. The same skip applies down-left: the Settings "‹ Back" button at the bottom-left could not be reached by Down from the toggle (three attempts left focus on the toggle); moving it into the same column as the toggle fixed it. Also: after dismissing a pushed screen with its Back button, focus returns to the element that pushed it — so a Down press from there goes to the grid (Central), not back into the pushed screen.
- **The Device Hub AX tree does not show tvOS focus movement** (already noted above) — and the runtime's stop-guidance fires on that blindness: three or four Down presses in a row report "no change observed" even while focus visibly moves and the list scrolls. Judge focus from screenshots, not the tree, and snap to confirm before pressing Return on a toggle or a theme button (a Return on the wrong focused element changes a setting).
- **TfL Arrivals feed emits placeholder rows before service starts** (v1.11, found live 23 Nov 2026): timeToStation ~41 s, expectedArrival "now", empty currentLocation/towards — and they can carry any platform name, so never filter on platformName. Filter on `timeToStation < 300 && currentLocation.isEmpty` — a genuinely approaching train has a location. Re-check board correctness in the daytime and for DLR, whose currentLocation behaviour is unobserved.
- **One station can need two stop points** (v1.11, proven live): Paddington's Tube lines come from `940GZZLUPAC`, its Elizabeth line trains from `910GPADTON` — neither covers the other. Liverpool Street is the same (v1.13, proven live): Tube lines from `940GZZLULVT`, Elizabeth line from `910GLIVST`. Do not assume a single stop point covers all of a station's lines; check the feed per line.
- **The run destination drifts back to a real TV between runs** (v1.13, 23 Nov 2026): the destination popup read "Samsung 55" at the start of the session and "projector" later, and the status line showed a stale "Running TubeNavigatorTV on Samsung 55" with a "The application failed to launch" sheet and a refused TCP connection — a launch attempt on the asleep/unreachable real TV that failed, so nothing was installed there. Re-select the simulator via the Filter + Return route before every Run, and trust only the settled status line. The stale real-TV status can persist across observations; the popupbutton value is the destination for the next run.
- **A right-aligned Refresh is skipped on the way down but reachable on the way up** (v1.13, verified): Down from the tab bar goes straight to the content and never lands on Refresh — the same skip as the v1.8 corner gear. Up from the top content row lands on Refresh, and Up from Refresh returns to the tab bar. So a corner control is not unreachable, just one Up press away; note it in the user manual rather than assuming Down reaches it.
- **A detail strip carrying three facts in one line truncates at TV type sizes** (v1.17, found live 23 Nov 2026): destination + segment + next stop on one `.title2` line ran off the right edge with ellipses. Split it into two lines (destination + next stop, then the segment in `.headline` secondary) and grow the strip's height (60 → 100pt) instead of shrinking the type.
- **The stale real-TV status can flash during a rebuild too, not just at session start** (v1.17, 23 Nov 2026): after the second Run click the status line briefly read "Running TubeNavigatorTV on Samsung 55" and the stack-frames popup read "TubeNavigatorTV : Samsung 55", while the destination popup read the simulator throughout — then both settled back to the simulator. The popupbutton value is the destination for the run; trust only the settled status.
